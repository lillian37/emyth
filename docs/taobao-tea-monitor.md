# 淘宝 App 内闪购茶饮订单提醒

此功能从用户明确开启的通知访问中识别淘宝 App 的茶饮订单线索，再由指定助手主动联系用户。
首版仅支持 `com.taobao.taobao`，不读取独立闪购 App、小程序页面、支付记录或订单接口，
也不拦截下单或付款。当前规则尚未用用户真实通知样本验证，不能承诺覆盖所有订单。

## 使用

在设置中打开「淘宝闪购茶饮提醒」，选择接收助手，允许系统通知访问，再开启自动提醒。
可以编辑茶饮品牌／商品识别词和提醒提示词。默认关闭，旧配置升级后也不会自动开启。
只有启用之后、最近三十分钟以内的通知才可能产生新的自动提醒；重连不会回放启用之前的订单。

## 判定与最少数据

确认规则要求同一条淘宝通知同时包含茶饮关键词、闪购／外卖线索和明确订单进展。
第一条收到的通知可以直接是配送进展，不要求先收到下单或付款通知。配送规则支持订单、餐品、
外卖或骑手“开始配送／已开始配送”，以及主体与进展之间的空格和换行。
通知不需要包含具体商品明细，但仍需命中奶茶店名或茶饮识别词；只有通用配送消息时仅记录，
不会自动联系助手。肯德基等综合餐饮店名不能单独证明订单中有茶饮，添加自定义词时需自行判断。
优惠推广、聊天、普通商品或快递、待付款、取消／退款等通知不会确认下单。缺少证据时仅记录
「待确认」依据，不自动唤醒助手；打开淘宝或普通付款成功本身都不是下单证明。

检测使用单条通知的标题、附加文字、正文及展开正文，跳过系统通知组汇总，防止跨消息拼接证据。
本地只保留有界的规则证据、时间、接收助手和处理状态，最多四十条可见记录。通知原文不会写入
这份记录或直接发给模型。模型只收到 JSON 中的命中词、订单阶段和时间；订单号和通知 key
仅用于本地去重，不进入模型上下文。用户原有通知缓存及工作流行为保持原样。

订单进展不等于购买数量，更不证明已经喝了多少；模型上下文明确保留这种不确定性。
提示词可编辑，助手原有的聊天设定仍生效。

## 去重与可靠性

- 优先用订单号合并同一订单的支付、备餐和配送进展；无订单号时先对通知身份使用二十分钟窗口。
  同一通知身份、相同茶饮证据的后续备餐／配送阶段还会在三小时生命周期内归并，避免一单配送
  超过二十分钟便再次联系。缺少订单号时仍无法完美区分另一单或换通知身份的同一单，不是精确计杯工具。
- 本地记录先持久化，再启动已有的后台生成服务；服务取得前台运行和 CPU 唤醒保护后原子抢占事件。
- 指定助手必须仍存在且与配置一致，不回退到别的助手；使用该助手实际最近更新的聊天。
- 会话繁忙时最多等待两分钟。仅在尚未开始任何模型／工具请求时才能释放事件并安排安全重试。
  重试工作只负责后台服务投递，每条工作链最多五轮待投递检查，事件总边界为三十分钟新鲜度。
  尚未开始生成的已抢占事件保留后续检查，避免等待聊天结束时丢失重试；已开始生成后不再次派发。
- 模型请求开始标记先持久化；开始后中断、进程被杀或结果不明均不自动重放模型／工具操作。
- 关闭功能或更换接收助手会阻止排队事件继续发送，并取消当前事件自己的生成，不影响其他会话。
- 只有回复实际写入聊天后才标「已生成并保存回复」；模型跳过、模型失败、取消或启动失败分别记录。
  清除本地记录不会让迟到的回调重新插回记录。

## 验证

JVM 回归测试覆盖证据判定、非茶饮／广告误报、字段边界、序列化默认配置、启用时间、
仅有茶饮品牌的首次配送通知、开始配送表述与空格变体、缺少茶饮线索的配送不触发、
同订单去重、事件抢占、开始请求后的重试禁止、重启恢复、清除记录以及最少模型上下文。
另运行现有应用单元测试与优化 APK 构建。真实通知是否含足够字段、通知权限和手机后台设置
仍需在 P60 上以下次实际订单验证；本次不宣称已经完成真实平台订单适配。
